# Git 与提交规范

## 一、铁律回顾
- **你永远不自己 `commit`**；commit 由用户批准后才执行。
- **合并进 `main`、`push` 一律用户操作**，你不许做。
- 你只在 `backend/` 内产生改动；不动前端文件。

## 二、分支
- 在 `main` 之外的**功能分支**上开发，一个功能切片一支。
- 命名：`feat/<模块>-<简述>`，如 `feat/auth-register`、`feat/movie-search`。其它类型：`fix/`、`refactor/`、`test/`、`db/`（迁移）。
- **不要**直接在 `main` 上改。

## 三、提交流程（每个切片完成后）
1. 自检：改动只在 `backend/`、切片功能完成、关键路径测试通过、报告已写。
2. `git add` 暂存**本切片相关文件**（按文件名加，**不要 `git add -A`/`git add .`**，以免误带 `.env`、`.claude/`、前端文件）。
3. 写好**提交信息草稿**（格式见下），输出给用户：「✅ 切片 X 完成，建议提交，提交信息如下，请批准」。
4. **等用户批准**，批准后才 `git commit`。
5. 合并到 `main` / `push`：交给用户。

## 四、提交信息格式（便于排错）
```
<类型>(<模块>): <一句话简述>

- 做了什么：……
- 为什么：……
- 关联报告：docs/progress/<报告文件>.md
- 如何回滚：revert 本提交即可 / 需注意的迁移或数据影响
```
类型：`feat`/`fix`/`refactor`/`test`/`docs`/`db`/`chore`。

示例：
```
feat(auth): 实现用户注册与待审核状态

- 做了什么：POST /api/auth/register，落库 status=pending；密码 BCrypt 加密
- 为什么：契约 1.1 + 课程"注册需管理员审核"要求
- 关联报告：docs/progress/20260601-auth-register.md
- 如何回滚：revert 本提交；本切片含 V2 迁移（仅加表，无数据风险）
```

## 五、注意
- 提交前确认 `.gitignore` 已忽略 `target/`、`.env`、本地配置、`.claude/`，**绝不提交密钥与构建产物**。
- 若 `git status` 出现 `backend/` 之外的改动，说明越界了——停下排查。

**Why:** 频繁、规范、可回滚的提交点，是出大问题时的救命稻草；但提交/合并的"扳机"必须握在用户手里。
**How to apply:** 切片完成 → 暂存 → 给草稿 → 等批准 → 提交；合并与推送永远交给用户。
