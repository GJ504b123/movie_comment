# 后端文档体系导览（给人看的）

> 这份文件是**给人读的总说明**：解释 `backend/` 里这套文档"哪部分写了什么、为什么这么编排、各部分怎么协同"。
> 如果你是来写代码的 AI（DeepSeek），请看 `../AI_README.md`，那是给你的精简导航；本文件是给**人**（项目负责人 / 队友 / 评审老师）看的设计说明。

---

## 1. 先讲清楚：这套文档为什么存在

本项目的后端代码**不是人逐行手写**的，而是由编码 AI（DeepSeek，经 Reasonix 工具）在本机以 **YOLO 全权限模式** 运行、由我用手机通过 **QQ 机器人** 远程指挥完成。

YOLO 模式意味着：**没有"每一步点同意"的人工关卡**——AI 可以直接读写文件、跑命令。方便，但危险。所以原本由"人在键盘前把关"的安全，现在**改用一套文档+流程来重建**。这就是 `backend/docs/` 的全部意义：

> **用文档把护栏写死，让一个全权限的 AI 也只能在安全的轨道里干活。**

### 分工一览

| 角色 | 是谁 | 负责什么 |
| --- | --- | --- |
| **指挥** | 我（项目负责人） | 用 QQ 远程下指令、审批提交、做 merge/push、拍重大决策 |
| **架构 & 治理** | Claude | 写 `backend/docs/` 这套架构文档与治理规则（**不写应用代码**） |
| **编码执行** | DeepSeek / Reasonix | 严格按文档和契约写后端 Spring Boot 代码 |
| **前端** | 队友 | 仓库根 `movie-review/` 的 Vue 前端（**后端不碰**） |

## 2. 编排逻辑：四层文档 + 两个外部锚点

整套文档不是一堆平铺的 md，而是按"**从总到分、从约束到实现**"分了四层，再加两个仓库内/外的"权威锚点"：

```
backend/
├── AI_README.md                 ← 入口层：AI 一进门先读这个（导航 + 红线速览）
├── docs/
│   ├── README.md                ← （本文件）给人看的体系说明
│   ├── governance/              ← 治理层：能不能做、怎么做才安全（约束 AI 的行为）
│   │   ├── 00-core-rules.md         七条安全铁律（最高优先级）
│   │   ├── 01-danger-and-blocking.md 危险清单 + 阻塞协议
│   │   ├── 02-git-and-commit.md      分支/提交/审批规范
│   │   ├── 03-module-report.md       每个切片写报告的模板
│   │   └── 04-secrets-and-security.md 密钥与安全
│   ├── architecture/            ← 架构层：系统大致长什么样（指导 AI 怎么实现）
│   │   ├── 00-system-overview.md     系统大图
│   │   ├── 01-techstack-and-conventions.md 技术栈+目录结构+阿里命名规范
│   │   └── 02-data-model.md          数据模型概要
│   └── progress/                ← 进度层：做到哪了、有什么卡住待批
│       ├── _index.md                进度索引
│       └── pending-approval.md       待审批事项（危险操作/重大决策记这）
│
└──（仓库根，非 backend/，但被反复引用）
    └── apiDesigner.md           ← 契约锚点：前端定的 API 契约（权威、只读）

（仓库外，不进 git）
~/.reasonix/memory/817629acfef4af19/   ← 记忆锚点：Reasonix 自动加载的常驻规则
    ├── MEMORY.md                       索引
    └── movie-backend-rules.md          铁律摘要，指针指回上面的 docs/
```

**为什么是这四层？**

1. **入口层（AI_README.md）**——AI 每次"开工"第一眼看到的东西，作用是**导航**：一句话背景、最容易踩的红线、该按什么顺序读后面的文档。它薄，只负责"把人引到对的地方"。
2. **治理层（governance/）**——回答"**什么能做、什么必须先停下问**"。这是护栏本身，优先级最高，和安全相关的内容**压倒一切其它指令**。
3. **架构层（architecture/）**——回答"**系统大致怎么搭、代码放哪、按什么规范命名**"。刻意只写"大致做什么"，不写太细，给 AI 留实现空间，但框住技术栈和结构。
4. **进度层（progress/）**——回答"**做到哪了、有什么在等我批**"。这是**人和 AI 之间的协作看板**：AI 在这里报进度、记待批事项，我在这里看进度、做审批。

**两个锚点为什么单列？**

- **契约锚点 `apiDesigner.md`**：在仓库根、是**前端队友写的、双方共同遵守的 API 契约**。它不归后端管（只读），但后端所有接口必须严格实现它，所以被反复引用。
- **记忆锚点（Reasonix memory）**：在**仓库外**的 `~/.reasonix/memory/<hash>/`，Reasonix 启动时会按"工作区路径的哈希"自动加载它（本项目 hash=`817629acfef4af19`）。它只放**摘要和指针**，真正的细节一律以仓库内 `docs/` 为准——这样规则跟着代码走、能进 git、可回滚。

## 4. 三个核心机制：文档是怎么"动起来"的

文档不是摆设，它们靠三条流程串成一个闭环：

### 机制一：开工先读（Read-First）
AI 每次新会话固定按顺序读：`AI_README` → `governance/00` → 其余 governance → architecture → 根 `apiDesigner.md` → `progress/_index.md`。
**目的**：确保它每次都"重新装载"全部护栏和上下文，不会因为换了会话就忘事。

### 机制二：危险即停（Danger → Block → Report → Wait）
```
AI 准备做某事
   │
   ├─ 命中危险清单？ ──否──► 直接做（按契约实现的正常 CRUD 不算危险）
   │
   └─是─► 立即停止 → 写 pending-approval.md → QQ 汇报 → 等我指令
                                              （等待期间可做其它安全的活）
```
**目的**：把删除/删库/破坏性操作这些"不可逆的事"全部拦在人工审批之后。

### 机制三：软提交审批（Soft-Commit Approval）
```
AI 完成一个切片 → 写切片报告 → git 暂存改动 + 起草提交信息 → QQ 请求批准
                                                              │
                                       我在手机上看 → 同意 ──► 提交 commit
                                                              │
                                            merge 进 main / push ──► 只能我自己做
```
**为什么是"软"约束**：提交不做成硬钩子拦截，因为我需要在手机上"批准后能提交"；硬拦截会把我批准的提交也一起挡掉。所以靠规则约束（AI 不自己提交），而不是技术上禁死。
**目的**：既能用 git 历史随时回滚大错误，又不让 AI 擅自污染主分支。

## 5. 作为"人"，你平时怎么用这套东西

- **想知道做到哪了** → 看 `docs/progress/_index.md` 和各切片报告。
- **AI 说"有事要你批"** → 看 `docs/progress/pending-approval.md`，在 QQ 上回复同意/否决。
- **AI 写完一个切片要提交** → 它会把暂存内容和提交信息草稿发你，你点同意它才提交。
- **合并到 main / push** → **永远是你自己操作**（AI 不做）。
- **排错** → 对着切片报告里的"怎么做的"定位问题。

## 7. 关键约定速查（契约里定死、架构里落实的）

| 约定 | 说明 |
| --- | --- |
| 影片删除 = **软删除** | `movie.deleted=true`，保留评论，不物理删 |
| 评分**去规范化** | `average_score` / `review_count` 冗余存表，评论变更时在**同一事务**里维护 |
| **一人一影评一条** | 同一用户对同一影片重复评论 → 409 |
| 访问日志 = **AOP 自动记录** | 不手写散落的埋点 |
| 统一返回体 | `{code, message, data}`；分页 `{list,total,page,size,totalPages}` |
| 鉴权 | JWT Bearer（前后端分离） |
| **两个契约缺口**（待你拍板） | ① 有 `likeCount` 字段但契约没有点赞接口；② 排行榜 `timeRange`"若实现" |
